# Architecture and ownership

Flutter Forge keeps composition in the application and behavior inside each feature. Schema-4 apps have a typed registry and two Forge-managed composition files. All other generated source belongs to the app. Legacy schemas retain manual composition.

## Generated application

`lib/main.dart` starts `App`. `lib/app/app.dart` owns a fresh GetIt container and the `GoRouter`, applies `theme.dart`, and builds `MaterialApp.router` with English gen-l10n delegates. `lib/app/dependencies.dart` registers infrastructure and feature factories. `lib/app/router.dart` retrieves factories only at the app composition root. Feature source never imports GetIt. Home uses the same route factory contract as later features.

`lib/core/network` contains Dio configuration, a transport-only client, and safe typed error mapping. There are no invented endpoints or request loggers. `API_BASE_URL` defaults to empty and requests fail before transport until configured. Generated clean models use Freezed with checked JSON mapping and a nonempty string converter. Models map to framework-independent entities. States use Freezed unions, Bloc events use immutable Freezed events, and notifier counter state remains an immutable integer. Code generation and localization commands are part of managed create, scaffold adoption, and feature generation.

The default clean feature has `data/datasources`, `data/models`, `data/repositories`, `domain/entities`, `domain/repositories`, `domain/usecases`, and `presentation` directories. The model validates an explicit starter string `id` and `title` contract. The repository catches only the feature's typed datasource exception and returns `fpdart.Either<Failure, Entity>`. Unexpected errors propagate. The domain does not depend on presentation or a project's shared core contracts.

The route factory requires a controller factory. The constructor chain is datasource, repository implementation, load use case, then the selected controller. Cubit and Bloc use `BlocProvider`, which owns and closes the controller. Riverpod uses a Riverpod 3 `Notifier<State>` and an auto-disposed provider overridden by a route-local `ProviderScope`. Provider uses `ChangeNotifier` owned by the route's `ChangeNotifierProvider`. No global provider scope is required. Pages render loading, error with retry, or content. Async loads do not publish results after disposal, and a newer request supersedes an older response. Managed app composition supplies explicitly named local starter datasources. A real adapter replaces the local datasource through `createDependencies(homeDatasource: adapter)` or the corresponding feature parameter, without editing the managed file.

Generated tests use fake datasources to exercise mapping, typed failure translation, programming-error propagation, loading, success, retry, and disposal. Notifier route tests leave the route while a load is pending, assert disposal, then re-enter to check that the route creates fresh state. Riverpod tests use `ProviderObserver` to observe disposal without exposing controller internals. The counter recipe exercises updates and ownership. All generated imports use package names from validated metadata.

Schema-4 feature generation renders the whole router and DI files from validated typed registry entries. Before writes, it compares their current contents and the metadata with the expected generated files. Edits, missing files, route collisions, and unsafe paths stop the operation. No user-supplied path can authorize replacement. The CLI does not merge arbitrary Dart source or provide a force flag. Legacy schemas write only absent feature directories and print manual wiring instructions. Pubspec and lint configuration are never changed by feature generation.

Managed codegen uses exact Forge localization, builder, and import-migration configuration. Alternate build configurations and redirected output settings stop generation. Output preflight checks source roots, every localization output, build-cache paths, and package metadata for links before writes, and repeats before dependency resolution. Builder inputs are constrained to feature Dart files. Dependency builders remain trusted code, not sandboxed plugins. Generated parts may be regenerated; exact-content ownership applies to integration and generator configuration files, not every regular generated output.

## CLI internals

`lib/src/cli/commands.json` defines the command catalog, option types, defaults, choices, and positional requirements. Its local `commands.schema.json` provides editor validation. Run `dart run tool/generate_commands.dart` from the repository root after edits to regenerate `commands.g.dart`. `command_definitions.dart` decodes and validates the embedded JSON, so installed snapshots and compiled executables need no adjacent source files. `options.dart` builds parsers generically and holds resolved command options. Common flags are registered at both parser levels rather than moved between tokens. `invocation_schema.dart` exports the JSON-backed parser metadata and positional definitions. `runner.dart` uses the positional bounds, chooses interactive or argument-only execution, orchestrates Flutter, and preserves the generation preflight. Command handlers and semantic checks remain Dart code.

`prompt.dart` collects omitted values through asynchronous line input. Its command names, option choices, and parser defaults come from the catalog. Runtime defaults and project inheritance remain in Dart. `PromptInput` injects terminal capability and input for tests. `runCli` also accepts the environment, output sinks, a working directory, and a `FlutterToolchain`. Injecting an output sink defaults terminal capability to false unless the caller supplies `PromptInput`, so tests do not inherit a developer's terminal.

`reporter.dart` owns the JSON envelope and human output policy. Operations fill structured data directly rather than capture human prose. The system toolchain sends its logs to stderr in JSON mode. Each handled execution path finishes one result.

`lib/src/project` validates identifiers and reads schema metadata. `lib/src/templates` contains bundled Dart strings, so templates also work in a compiled executable. `GenerationPlan` describes complete relative file contents and required-absent directories. `FileWriter` checks paths and collisions before writing. `SystemFlutterToolchain` locates Flutter and streams subprocess output.

`FeatureArtifact` owns a generation plan and `FeatureWiring`. Text instructions and structured JSON derive from the same imports, route entry, datasource parameter, controller expression, and validated static location. App Home composition uses that same model. Import ordering and formatting occur in memory, without a formatter process or source mutation during preview.

`profiles.dart` defines the four `StateStyle` choices shared by CLI, metadata, dependencies, and templates. State-specific emitters share clean domain/data files and state classes. They do not share a presentation abstraction that erases each package's APIs. Notifier templates qualify backend and UI references so generated names such as `ChangeNotifier` and `StreamNotifier` cannot shadow imported framework types. `FeatureWiring` keeps route registration and lifecycle instructions backend-specific.

Schema 4 adds typed `features` entries to the package, recipe, lint profile, and state fields in schema 3. Schemas 1 and 2 retain Cubit without rewriting metadata. Schema 1 also retains counter and Flutter lints. The dependency inventory varies by state management, recipe, lint profile, and managed infrastructure. It drives pubspec generation, app-name conflicts, and dependency preflight. Riverpod also reserves its required transitive package name `riverpod`, without installing it directly. New apps use Very Good Analysis unless explicitly overridden. Only `public_member_api_docs` is disabled because generated apps do not publish a library API.

The create flow validates the absent target, runs Flutter's platform generator, applies the limited fresh-scaffold overlay, resolves dependencies, and generates code. Init defaults to metadata-only adoption with missing-dependency warnings. Explicit `init --scaffold` requires dependencies and pubspec settings first, refuses occupied integration paths, and adds an alternate `main_forge.dart` entrypoint without replacing existing source. Managed operations run code generation unless `--no-pub` is supplied. Dry runs never write files or start processes. Failure and interruption limits are in the [command reference](commands.md#exit-codes-and-interrupted-generation).
